# ADR-0002: 시트 4개 데이터 모델과 CSV 기반 빌드

- 상태: 제안됨
- 날짜: 2026-11-20
- 근거: [PRD v0.6](../prd/PRD-v0.6.md) §5, §6, §8 F3·F5·F9, §9, §11 / [CTO v0.5 리뷰](../reviews/v0.5/5-CTO.md) 지적 3
- 관련: [tech-stack.md](../architecture/tech-stack.md) §5, [data-validation.md](../architecture/data-validation.md), [ADR-0001](0001-static-site-and-light-pwa.md)

## 배경

- PRD §9는 스프레드시트 하나에 시트 4개(`cafes`, `chains`, `methods`, `stations`)를 두고, 각 시트를 CSV로 내보내 정적 사이트 생성기로 빌드한다고 정했다(§11).
- 한 카페가 추출 방식을 여러 개 가질 수 있고, 방식마다 출처·날짜가 따로 붙는다(§5, §6). 그래서 방식은 별도 시트(`methods`)에 한 행씩 둔다.
- 체인 매장은 자기 방식 행이 없고 체인의 방식을 따른다(§5, F3, F9, §19 #4).
- CTO v0.5 리뷰는 두 가지를 지적했다. 첫째, 무결성 규칙을 강제하는 장치가 없다. 둘째, 시트가 CSV가 되는 방법(수동 내보내기 4번)이 현실적인 실패 지점이다.

## 결정

1. **원본은 Google Sheets 하나, 시트 4개.** 열과 의미는 PRD §9를 그대로 따른다. 이 ADR은 열을 새로 추가하지 않는다.
   - `methods` 한 행은 카페 또는 체인 중 **정확히 하나**에 속한다(`cafe_id` XOR `chain_id`).
   - 체인 매장(`cafes.chain_id`가 있음)은 방식 행을 갖지 않는다. 화면·필터는 체인의 방식 행을 쓴다.
   - `station_id`는 빌드 때 좌표로 계산한다. 가장 가까운 대상 역을 하버사인 직선거리로 고른다.
2. **CSV는 스크립트로 받아 레포에 커밋한다.**
   - `scripts/fetch-sheets`가 "웹에 게시"한 시트 4개의 CSV URL에서 받아 `data/{cafes,chains,methods,stations}.csv`에 쓴다.
   - 데이터 변경은 커밋 → PR → CI 검증 → main 머지 → 배포 순서로 진행한다. 롤백은 커밋 되돌리기다.
3. **배포 전 검증을 거친다.** 검증 스크립트가 [data-validation.md](../architecture/data-validation.md)의 규칙을 확인한다. 오류가 하나라도 있으면 빌드와 배포를 멈춘다. 그동안 사이트는 마지막으로 성공한 배포 상태로 남는다.
4. **공개하면 안 되는 데이터는 게시 범위 밖에 둔다.**
   - Google Form 응답 시트는 게시하지 않는다(연락처 포함, F5).
   - `cafes.internal_note`는 게시 CSV와 공개 레포로 나가면 안 된다(§9 "Never published"). **제안:** 게시하지 않는 별도 시트로 옮긴다. PRD §9를 바꾸는 일이라 창업자가 결정해야 한다. 그 전까지 검증 스크립트는 받은 CSV에 `internal_note` 값이 있으면 오류로 처리한다.

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| 한 시트에 방식을 열로 펼침(`espresso`, `hand_drip` … 열마다 출처·날짜) | 열이 방식 수 × 4개로 늘어난다. 방식이 하나 늘 때마다 스키마가 바뀐다. v0.3 planner 리뷰(B4)가 이미 행 단위 분리를 요구했다 |
| JSON/YAML 파일을 레포에서 직접 편집 | 창업자가 휴대폰으로 시트를 고치는 흐름(F5)과 맞지 않는다. 비개발자 협력자를 받기도 어렵다 |
| 수동 내보내기(탭 4번 다운로드) | 정정할 때마다 반복하는 수작업이고, 파일 이름·탭을 혼동하기 쉽다 |
| CI가 빌드할 때마다 게시 CSV를 직접 받음 | 데이터 이력이 레포에 남지 않고 같은 커밋의 빌드 결과가 달라진다. 변경을 diff로 확인할 기회가 없다 |
| Google Sheets API + 서비스 계정 | 시트를 비공개로 둘 수 있지만, 자격 증명과 GCP 설정이 이 규모에는 과하다 |
| SQLite 등 DB 파일 | 백엔드가 없는 구조(ADR-0001)에서 이점이 없고 편집 도구가 늘어난다 |

## 결과

**좋은 점**
- 데이터 변경이 git 이력으로 남는다. 무엇이 언제 바뀌었는지 PRD §12의 정확도 재확인 때 추적할 수 있다.
- 무결성 규칙이 문서가 아니라 코드로 강제된다.
- 같은 커밋은 항상 같은 사이트를 만든다.

**나쁜 점 / 감수할 것**
- 시트를 "웹에 게시"하므로, 게시한 4개 시트의 내용은 링크를 아는 누구나 볼 수 있다. 사이트에 공개되는 정보와 같으므로 받아들인다. 단, `internal_note`는 분리해야 한다.
- 게시 CSV는 시트 변경 후 반영까지 몇 분 걸릴 수 있다(Google 도움말, 2026-11-20 확인: https://support.google.com/docs/answer/183965).
- 데이터만 고칠 때도 PR 단계를 거친다.
- 시트 구조(열 이름)를 바꾸면 검증 스크립트와 빌드 코드도 같이 바꿔야 한다.
